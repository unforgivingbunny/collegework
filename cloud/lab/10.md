## Короткі теоретичні відомості

**Docker** — це відкрита платформа для розробки, доставки та запуску застосунків у контейнерах. Контейнери дозволяють ізолювати програмне середовище, що забезпечує незалежність від середовища виконання та спрощує розгортання.

* **Контейнер (Container)** — легкий, ізольований процес з власною файловою системою, мережевим інтерфейсом та обмеженими ресурсами.
* **Образ (Image)** — шаблон (багатошаровий файл лише для читання), з якого запускається контейнер.
* **Docker Engine** — клієнт-серверний рушій, що виконує команди Docker, керує образами та контейнерами.
* **Docker Hub** — публічний хмарний реєстр Docker-образів.
* **Dockerfile** — текстовий файл зі сценарієм автоматизованого складання образу.

### Відповіді на питання (Answers to Questions):

#### 1.1. Діаграма архітектури Docker (Docker Architecture Diagram)

Docker використовує клієнт-серверну архітектуру. Взаємодія між ключовими компонентами виглядає так:

```text
+-------------------------------------------------------------------+
|                           DOCKER HOST                             |
|                                                                   |
|  +-----------------------+       +-----------------------------+  |
|  |     Docker Client     |       |        Docker Daemon        |  |
|  |  (CLI: docker run,    | ----> |         (dockerd)           |  |
|  |   docker build, pull) | REST  |  Manages Images, Containers |  |
|  +-----------------------+  API  |  Networks, and Volumes      |  |
|                                  +--------------+--------------+  |
|                                                 |                 |
|                                  +--------------v--------------+  |
|                                  |  Images  <--->  Containers  |  |
|                                  +--------------+--------------+  |
+-------------------------------------------------|-----------------+
                                                  | Pull / Push
                                                  v
                                   +-----------------------------+
                                   |       Docker Registry       |
                                   |   (Docker Hub / Private)    |
                                   +-----------------------------+
```

* **Docker Client:** The primary command-line interface (`docker`) that accepts user commands and communicates with the daemon via a REST API over UNIX sockets or a network interface.
* **Docker Daemon (`dockerd`):** The background service running on the host machine that listens for Docker API requests and manages Docker objects (images, containers, networks, and volumes).
* **Docker Registry:** A centralized repository for storing and distributing Docker images (e.g., Docker Hub, Amazon ECR, Azure Container Registry).

#### 1.2. Чим відрізняється Docker-контейнер від Docker-образу?
* **Docker Image:** A read-only, immutable template composed of layered filesystems containing application source code, runtime, system libraries, and dependencies. *Analogy: a class definition in OOP or an ISO installation image.*
* **Docker Container:** A runnable, isolated instance of a Docker image. It adds a thin writable layer (container layer) on top of the underlying read-only image layers and possesses its own isolated process space, filesystem, and network stack. *Analogy: an instantiated object of a class.*

#### 1.3. Як можна подивитися список запущених контейнерів?
* To display **only currently running** containers:
  ```bash
  docker ps
  ```
* To display **all** containers on the host (including stopped and exited instances):
  ```bash
  docker ps -a
  ```

#### 1.4. Як передати локальний порт до контейнера?
Port forwarding (publishing) is configured using the `-p` (or `--publish`) flag during container launch with the syntax `-p <HOST_PORT>:<CONTAINER_PORT>`.
* *Example:* `docker run -d -p 8080:80 nginx` maps TCP port `80` inside the container to TCP port `8080` on the local host machine.

#### 1.5. Як можна зв'язати кілька контейнерів між собою?
1. **User-Defined Bridge Networks (Recommended):** Create a custom isolated network (`docker network create app-net`) and attach containers using `--network app-net`. Docker's embedded DNS server automatically resolves container names to their internal IP addresses.
2. **Docker Compose:** Define multi-container services in a declarative `docker-compose.yml` file, which automatically provisions a shared virtual network and manages startup dependencies.

## 3. Контрольні питання (Review Questions)

### 3.1. У чому полягає відмінність між `docker stop` і `docker rm`?
* **`docker stop`:** Gracefully stops a running container by sending a `SIGTERM` signal to its main process (`PID 1`), allowing it to close connections and clean up resources (if it does not stop within 10 seconds, `SIGKILL` is sent). The container's writable filesystem layer, configuration, and logs remain intact on disk, and it can be restarted with `docker start`.
* **`docker rm`:** Permanently deletes a stopped container along with its writable filesystem layer, metadata, and network mappings from the Docker host. Once removed, the container state cannot be recovered.

### 3.2. Які є альтернативи Docker? Зробіть порівняння їх можливостей.

| Критерій порівняння | Docker | Podman | containerd |
| :--- | :--- | :--- | :--- |
| **Архітектура** | Клієнт-серверна (потрібен постійно запущений фоновий демон `dockerd`) | Бездемонна / Daemonless (контейнери запускаються як дочірні процеси через `fork/exec`) | Легковаговий низькорівневий container runtime (ядро виконання для Kubernetes) |
| **Rootless режим** | Підтримується як додаткова опція, потребує окремого налаштування | Нативна підтримка запуску від імені звичайного користувача за замовчуванням | Підтримується через rootlesskit |
| **Сумісність CLI** | Еталонний стандарт синтаксису CLI | 100% сумісність команд із Docker (`alias docker=podman`) | Власний низькорівневий CLI (`ctr`, `nerdctl`) |
| **Робота з Pod / Оркестрація** | Docker Compose, Docker Swarm | Нативна підтримка концепції Kubernetes Pods та генерація Kubernetes YAML | Стандартний високонадійний runtime для кластерів Kubernetes |

### 3.3. Що таке rootless-контейнеризація? Наведіть приклади та пояснення до них.
* **Rootless containerization** is a security execution model where both the container runtime engine and the containers themselves run entirely under an unprivileged regular user account, without requiring `root` (superuser) privileges on the host operating system. It relies on Linux **User Namespaces** (`uid_map` / `gid_map`) to map the `root` user inside the container (`UID 0`) to an unprivileged high-numbered UID on the host (e.g., `UID 100000`).
* **Examples:**
  * **Podman:** Built from the ground up with rootless execution as its default mode of operation.
  * **Docker Rootless Mode:** Configured via `dockerd-rootless-setuptool.sh install`, running the entire Docker daemon inside a user namespace.

### 3.4. Як впливає rootless-контейнеризація на безпеку?
* **Mitigation of Container Escape Exploits:** If an attacker exploits a vulnerability in the container runtime or kernel and breaks out of the container onto the host OS, they only inherit the limited permissions of an unprivileged host user rather than full `root` administrative control.
* **Enforcement of the Principle of Least Privilege:** Prevents containerized processes from modifying host kernel modules, system configuration directories (`/etc`, `/boot`), or accessing files owned by other system users.

### 3.5. Яку роль відіграє контейнеризація в хмарних технологіях?
* **Environment Portability ("Build once, run anywhere"):** Packages application binaries together with all system dependencies, eliminating configuration drift between local laptops, CI/CD pipelines, and public clouds (AWS, Azure, GCP).
* **Microservices & Elastic Scaling:** Enables decomposing monolithic systems into lightweight, stateless microservices that cloud orchestrators (Kubernetes, AWS ECS, Google Cloud Run) can spin up or scale down within milliseconds in response to traffic spikes.
* **High Resource Density:** Shares the host OS kernel instead of virtualizing hardware for every instance, significantly lowering cloud compute and licensing costs compared to traditional virtual machines.
